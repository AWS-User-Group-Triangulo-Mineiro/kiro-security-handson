ETAPA 01

Preparação do ambiente

Tempo sugerido: 60–90 minutos (ou 12 minutos de demonstração com as versões previamente preparadas). Você vai construir duas versões de uma API de tarefas em Java, explorar uma falha intencional e corrigir a autorização.

  • Instale o Kiro IDE e entre na sua conta.
  • Instale JDK 21, Maven 3.9+ e Git.
  • Use somente dados fictícios e mantenha a API em localhost. Não publique a versão vulnerável em um servidor.
java -version
mvn -version
git --version

No terminal, crie a pasta de trabalho e abra-a pelo menu File → Open Folder no Kiro.

mkdir secure-tasks-api
cd secure-tasks-api
git init
ETAPA 02

Lab 01 — versão vulnerável (controle experimental)

No chat do Kiro, solicite uma implementação local mínima. A vulnerabilidade é introduzida deliberadamente em um único endpoint de leitura para fins educacionais. Revise o plano e as permissões antes de aceitar alterações. Não use credenciais reais.

Crie um projeto Maven Java 21 com Spring Boot 3 (versão estável compatível), Spring Web, Spring Security, Spring Data JPA, H2, Validation, Spring Boot Test e Spring Security Test.
Nome: secure-tasks-api. Pacote: br.com.awsgugtm.tasks.
Configure server.address=127.0.0.1 e server.port=8080; H2 em memória e console H2 desabilitado. Não habilite CORS global nem endpoints de gestão.
Crie a entidade Task com id Long atribuído (sem geração automática), title e owner (username). Use DTO de resposta id e title. Crie dados fictícios: tarefa 42 de alice, tarefa 43 de bob.
Configure HTTP Basic apenas para este laboratório local com dois usuários in-memory fictícios: alice/alice-demo e bob/bob-demo. Use PasswordEncoder BCrypt para armazenar as senhas em memória. Todos os endpoints exigem autenticação. Mantenha a proteção CSRF padrão; o lab tem apenas leitura.
Implemente GET /api/tasks/{id}, GET /api/tasks (listagem filtrada pelo usuário autenticado). No endpoint por ID, introduza INTENCIONALMENTE a falha didática BOLA: buscar por ID somente, sem verificar owner. Rotule claramente o código vulnerável. Retorne 404 se inexistente.
Não implemente escrita, deploy, integração externa ou ferramentas MCP. Inclua testes MockMvc de Alice (200), anônimo (401), inexistente (404) e um teste de caracterização que mostra Bob acessando 42 (200).
Apresente o plano, aguarde minha aprovação e implemente em etapas. Ao final informe como rodar e testar.

Verifique pom.xml, a configuração de segurança, o repositório, DTO e dados de teste. Rode os testes e a API em terminais separados:

mvn clean verify
mvn spring-boot:run

Se houver erro, envie ao Kiro somente o trecho relevante da saída, sem tokens ou dados privados. Confira se o servidor está escutando apenas em 127.0.0.1.

ETAPA 04

Lab 02 — Steering e especificação segura

Abra o painel Kiro → Steering e gere os documentos de contexto se desejar. Em seguida, crie .kiro/steering/security.md com as seguintes instruções. Elas orientam o agente, mas não são controles de acesso.

---
inclusion: always
---
# Segurança do projeto
- Toda consulta de recurso deve respeitar a identidade autenticada.
- Nunca confiar em owner recebido do cliente.
- Usar DTOs e validação; não retornar entidades diretamente.
- Não incluir segredos, dados reais ou PII em logs e prompts.
- Incluir testes positivos e negativos de autorização.
- Não executar deploy; não acessar serviços externos; revisar comandos.
- Nunca desabilitar controles apenas para fazer testes passarem.
- Solicitar revisão antes de alterações em segurança.

Crie uma Feature Spec pelo painel Specs ou pelo modo Spec no chat e escolha o fluxo Requirements-First, se solicitado. O nome e a localização dos botões podem variar por versão.

Crie uma Feature Spec chamada secure-task-access para corrigir a autorização por objeto na API existente. Não implemente ainda.
Requisitos: toda tarefa é privada; identidade obtida do Spring Security; proprietário consulta com 200; usuário autenticado não proprietário recebe 404 sem revelar existência; não autenticado recebe 401; ID inexistente recebe 404. Listagem retorna somente tarefas próprias.
Design: consulta por id e owner em uma única operação no repositório, uso de DTO, ausência de credenciais reais e logs sem dados sensíveis. Analise o fluxo de identidade e os limites de confiança.
Tasks: criar primeiro teste de regressão que espera 404 para Bob; demonstrar falha na versão atual; implementar correção mínima; repetir testes e revisar diff.
Mantenha a configuração local e não altere testes para mascarar defeitos. Aguarde aprovação de requirements, design e tasks em cada fase.

Revise os artefatos na spec: requirements.md, design.md e tasks.md. A localização normalmente fica em .kiro/specs/secure-task-access/.

Critério de aceitação de exemplo

WHEN um usuário autenticado solicita uma tarefa pertencente a outro usuário, THE SYSTEM SHALL retornar HTTP 404 sem expor os dados do recurso.

ETAPA 05

Teste vermelho → correção → teste verde

Execute tarefas individuais na spec. Comece apenas pelo teste de regressão: substitua o teste de caracterização que aceitava o acesso indevido por outro que exige 404. O teste deve falhar pelo motivo esperado.

mvn test

Depois, execute a tarefa de correção. Se precisar orientar o Kiro, use:

Implemente somente a tarefa de correção BOLA aprovada. Obtenha o username do principal autenticado. Altere a consulta para findByIdAndOwner(id, username) com Optional<Task> e mapeie ausência para 404. Não aceite owner de parâmetros ou headers do cliente. Preserve os demais comportamentos. Execute todos os testes e mostre o diff. Não faça commit automaticamente.

Exemplo conceitual de repositório e chamada (adapte aos nomes efetivos gerados pelo Kiro):

Optional<Task> findByIdAndOwner(Long id, String owner);
// No serviço/controller, username vem do Principal autenticado:
return repository.findByIdAndOwner(id, principal.getName())
    .map(task -> new TaskResponse(task.getId(), task.getTitle()))
    .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
mvn clean verify
mvn spring-boot:run

ETAPA 06

Hooks, permissões e revisão

No painel Hooks, crie uma automação acionada por conclusão de tarefa de spec (ou evento equivalente disponível). Configure uma revisão de alterações e execução de testes, sem ações externas. Evite loops de hooks.

Ao concluir uma tarefa da spec, revise apenas as alterações deste projeto procurando ausência de autorização por objeto, exposição de segredos, mudanças inesperadas na configuração de segurança e falta de testes negativos. Sugira correções, sem aplicá-las automaticamente. Execute mvn test apenas com minha aprovação. Não faça deploy nem chame ferramentas externas.

Revise as permissões do agente; não autorize comandos arbitrários, acesso a produção ou MCP desconhecido. Um hook não substitui um gate obrigatório no CI.

Solicite uma revisão final independente:

Faça uma revisão de segurança da branch atual, somente leitura. Verifique autorização por objeto em todos os endpoints, identidade autenticada, DTOs, configuração local, exposição de dados, dependências, testes negativos e segredos. Liste achados por severidade com arquivo, linha e evidência. Não altere arquivos até aprovação.
git diff
git status
mvn clean verify
ETAPA 07

CI e entrega segura

Opcional: adicione o arquivo .github/workflows/ci.yml à aplicação segura. Este exemplo executa testes; análise SAST/SCA e secret scanning são etapas adicionais que precisam de ferramentas e configuração apropriadas. Configure proteção de branch para exigir o check antes do merge.

name: CI
on:
  pull_request:
  push:
    branches: [main, lab-seguro]
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - run: mvn -B clean verify

Revise e versione a versão segura localmente. Não faça push das branches/tags vulneráveis para repositórios públicos. Se quiser publicar a aplicação corrigida, crie um repositório limpo com o snapshot seguro, sem histórico vulnerável nem segredos, revise antes e não configure deploy.

git add .
git diff --cached
git commit -m "fix: enforce task ownership and regression tests"
ETAPA 08

Desafio extra e checklist

Proponha uma evolução: permitir alteração de título da tarefa com PATCH. Antes de gerar código, especifique autorização por proprietário, validação do tamanho e testes negativos. Se usar autenticação de sessão/browser, preserve e teste CSRF; não desabilite a proteção por conveniência.

Questões para discussão: por que UUID não resolve autorização? Por que escolher 404? Por que steering não é controle de segurança? Como o CI comprova que a regressão não voltou?

ETAPA 09

Publicar este tutorial no GitHub Pages

Crie um repositório vazio chamado kiro-security-handson na organização da comunidade. Copie apenas o index.html e o README deste pacote para uma pasta separada do código da API. No terminal dessa pasta:

git init
git add index.html README.md
git commit -m "docs: Kiro security hands-on"
git branch -M main
git remote add origin https://github.com/SUA-ORGANIZACAO/kiro-security-handson.git
git push -u origin main

Substitua SUA-ORGANIZACAO pela organização correta. No GitHub, abra Settings → Pages → Build and deployment → Deploy from a branch → main → / (root) → Save. O endereço será exibido pelo GitHub após publicar. Nenhum backend é necessário.
